# Аккаунты и вход

Статус: **черновик** (2026-10-22). Ждёт «ок» Анны и ответов на открытые вопросы (раздел 18).
План: [accounts.plan.md](accounts.plan.md). Журнал: [accounts.metrics.md](accounts.metrics.md).
Опирается на [batch-ux.md](batch-ux.md) (BN — «нет связи», очередь изменений) и CLAUDE.md §1–2 (данные у владельца, место под авторизацию).

Обозначения правил: **D** — изоляция данных и хранилище, **L** — вход по коду, **S** — сессии, **I** — приглашения,
**U** — пользователи (админка), **N** — стартовый набор, **M** — письма, **P** — страница аккаунта и «какие данные храним»,
**Q** — очередь изменений и истёкшая сессия, **C** — защита API, **X** — перенос данных Анны, **T** — обязательные тесты.

---

## 1. Цель

Сейчас CoveyPlanner — приложение одного человека без входа: кто открыл адрес, тот видит всё.
Нужно: несколько пользователей на одном сервере, у каждого свои данные; вход без паролей — кодом на почту;
регистрация по приглашениям Анны. Пока всё работает на компьютере Анны; деплой — следующая спека.

## 2. Термины

| Слово | Смысл |
|---|---|
| **Пользователь** (аккаунт) | почта + свои данные планировщика. Один человек — один аккаунт |
| **Администратор** | пользователь с флагом IsAdmin. Сейчас — только Анна |
| **Код входа** | 6 цифр из письма, живёт 10 минут, одноразовый |
| **Сессия** | одно вошедшее устройство/браузер; cookie на нём + запись на сервере |
| **Приглашение** | одноразовая ссылка со сроком; по ней можно один раз зарегистрироваться |
| **Почтовый ящик разработки** | папка, куда складываются письма вместо отправки (пока нет SMTP) |
| **Режим регистрации** | `Invite` (только по приглашениям, по умолчанию) или `Open` (любой адрес) — настройка сервера |

## 3. Анализ и рекомендации (A–D)

### A. Изоляция данных: одна база + UserId или файл на пользователя

Что есть в коде сейчас (важно для сравнения):
- 7 корневых таблиц данных (`Tasks`, `Categories`, `Roles`, `WeeklyGoals`, `GoalSeries`, `Vacations`, `AppSettings`) и 6 таблиц связей
  (`TaskRoles`, `TaskGoals`, `GoalRoles`, `GoalSeriesRoles`, `VacationHabits`, владеемые записи). `AppSettings` — **одна строка с Id = 1**.
- 8 репозиториев (`EfRepositories.cs`) ищут по Id без всякого «чьё»; ссылки из запросов клиента — голые Id: `roleIds`, `categoryId`, `parentId`,
  `projectId`, `seriesId` у каникул, место назначения `TaskTargetDto`.
- Запросы через навигации и подзапросы: `EfHabitRepository` (`Set<TaskGoal>()` → `l.Task`, `l.Goal.Series`, `db.GoalSeries.Any(...)`),
  `GetTrashedAsync` (`db.Tasks.Any(...)` внутри).
- `SeedData` — роли «на пустую базу», `BackupService` — `VACUUM INTO` одного файла, `tools/backup.ps1` и `install.ps1` — `POST /api/backup`.
- ~60 маршрутов API в 11 файлах `Endpoints/`.

| | (а) одна база + UserId + глобальный фильтр EF | (б) файл SQLite на пользователя + общая `accounts.db` |
|---|---|---|
| **Риск утечки** | Фильтр защищает **чтение**, но не **запись по чужому Id**: `roleIds`, `categoryId`, `parentId`, `projectId`, `seriesId` из запроса надо проверять в каждом сервисе, иначе своё дело можно привязать к чужой роли/проекту (а потом увидеть её название в своём DTO). Фильтр не действует на `FromSql`, `IgnoreQueryFilters`, `ExecuteUpdate` без условия, а у таблиц связей (`TaskGoal` как сущность) нужен свой фильтр — EF предупреждает о «обязательной навигации к фильтруемой сущности». Одна забытая проверка — утечка | Чужих строк в открытой базе **физически нет**. Единственное место, где можно ошибиться, — выбор файла по сессии (одна функция, один тест). Чужой Id просто не находится (или находит своё дело с тем же номером) |
| **Миграции схемы** | одна база — как сейчас | N файлов: при запуске сервер мигрирует `accounts.db` и каждый файл пользователя (перед этим — копия, как сейчас «перед-обновлением»). Для десятков пользователей — секунды |
| **Миграция под аккаунты** | новая миграция: `UserId` в 7 таблиц, индексы с UserId, `AppSettings` — ключ по UserId; данные Анны — `UPDATE ... SET UserId` | **схема данных не меняется вовсе**; файл Анны становится её файлом (копия `VACUUM INTO`) — сверка «до/после» совпадает по построению |
| **Бэкапы** | один файл — как сейчас | папка-снимок: `accounts.db` + все файлы пользователей; восстановить одного пользователя — один файл |
| **Выгрузка / удаление аккаунта** | выгрузка — запросы с фильтром; удаление — `DELETE` по UserId в правильном порядке по 13 таблицам (каскады, связи) | выгрузка — всё из одного файла; удаление — удалить файл (+ `-wal`, `-shm`) и строку пользователя |
| **Путь к PostgreSQL** | прямой: та же схема | хуже: или база/схема на пользователя в PostgreSQL, или тогда уже переход к (а). Код Core не меняется в обоих случаях — хранилище за интерфейсами |
| **Объём переделки** | миграция, фильтры, UserId при создании (7 фабрик или перехватчик), проверка владения всех входящих Id в ~20 методах сервисов, `AppSettings`, `SeedData`; тесты на каждую ссылку | выбор строки подключения по сессии (`AddDbContext`), второй `DbContext` для аккаунтов, мигратор по файлам, бэкап папкой. **Planner.Core и репозитории — без изменений** |

**Рекомендую (б) — файл на пользователя.** Аргументы по нашему коду: (1) главный риск — запись по чужому Id — в (а) закрывается только дисциплиной
в каждом сервисе, а в (б) его нет по устройству; (2) `AppSettings` с Id = 1, `SeedData`, `HabitRepository` с подзапросами — всё остаётся как есть;
(3) перенос данных Анны — копия файла, без переписывания строк; (4) «удалить аккаунт» — удалить файл, «выгрузить» — прочитать файл.
Цена — путь к PostgreSQL: при сотнях пользователей или переезде на PostgreSQL придётся перейти к (а); для приглашённых знакомых на домашнем
сервере или маленьком VPS SQLite-файлов хватит с запасом. Это решение фиксируется в спеке (D7), чтобы пересмотреть его при деплое, если нужно.

### B. ASP.NET Core Identity или своя модель

Identity рассчитан на пароли: 7 таблиц (`AspNetUsers`, `Roles`, `Claims`, `Logins`, `Tokens`, …), из которых нам нужна одна. Код на почту в Identity —
TOTP-токен (`EmailTokenProvider`): он **не хранится** (вычисляется из SecurityStamp), окно ~3 минуты с допуском, «10 минут», «5 попыток на код»,
«только последний код действует» и «частота по почте» пришлось бы надстраивать сверху. Список сессий и «выйти на всех устройствах» в Identity
тоже нет (только смена SecurityStamp).

**Рекомендую свою небольшую модель** (4 таблицы в `accounts.db`: Users, LoginCodes, Invites, Sessions) **+ стандартная cookie-аутентификация
ASP.NET Core** (`AddAuthentication().AddCookie()`, `AddAuthorization`, Data Protection). Шифрование cookie, политики, `[Authorize]`/`RequireAuthorization` —
готовые и проверенные; своё — только правила кода и приглашений (чистые функции в `Planner.Core/Accounts`, unit-тесты на каждое правило).
Самописной криптографии нет: случайность — `RandomNumberGenerator`, хэш — HMAC-SHA256, сравнение — `CryptographicOperations.FixedTimeEquals`.

### C. Защита API

- **Все маршруты `/api` закрыты по умолчанию** (`FallbackPolicy` = вошедший пользователь); открыты только явно помеченные `AllowAnonymous`
  (запрос и проверка кода, проверка приглашения, `ping`); админские — политика `Admin`. Тест перечисляет все маршруты (T1) — новый
  эндпоинт без пометки роняет тест.
- **«Это моё»** — устройством хранилища (D): контекст данных запроса открывается только на файл вошедшего пользователя; без пользователя
  контекст данных не создаётся вовсе (исключение — ошибка 500, а не «чей-то файл»). Плюс тест «А не видит и не меняет данные Б» по всем маршрутам (T2).
- **CSRF**: cookie `SameSite=Lax`; все изменяющие запросы (не GET/HEAD) к `/api` обязаны нести заголовок `X-Planner: 1` и, если браузер прислал
  `Origin`, — свой. Чужая страница не может поставить свой заголовок без CORS-preflight, а CORS не включаем. Antiforgery-токены не нужны.
  GET не меняют данных — кроме ленивого создания целей постоянных серий в `GET /api/week` (идемпотентно, безвредно; отмечено).
- **Частота** — встроенный `Microsoft.AspNetCore.RateLimiting` (по адресу) + счёт в `LoginCodes` (по почте, переживает перезапуск); 429 с
  понятным текстом (L5). Общий лимит API на пользователя — 600 запросов в минуту (от зацикленного клиента, не мешает обычной работе).
- **Логи**: не пишем коды, ссылки и токены приглашений, cookie и Id сессий, тела запросов, названия и заметки дел; почту — маской `a***@gmail.com`.
  `EnableSensitiveDataLogging` — никогда. Токен приглашения — во фрагменте ссылки (`/invite#…`), он не уходит на сервер в строке запроса и не попадает
  в журналы и `Referer`. Ответы об ошибках — без стека (как сейчас, ProblemDetails).
- **Заголовки**: `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY`.

### D. localhost: вход нужен или «локальный режим»

**Рекомендую: вход нужен всегда, и локально тоже; «режима одного пользователя» в продукте нет.** Причина: обход по «запрос с localhost» ненадёжен —
за обратным прокси (Caddy/nginx на той же машине, Tailscale Serve) все запросы приходят с localhost, и обход открыл бы всё всем. Неудобства нет:
сессия долгая (S2), вход раз в несколько месяцев; код читается в почтовом ящике разработки (M2) по ссылке прямо с экрана входа.
Для разработки и e2e — `POST /api/dev/login` (только окружение Development, как уже существующий `/api/dev/clock`): впускает по почте без кода.
Один e2e-сценарий проходит настоящий вход через почтовый ящик (T4).

## 4. Хранилище и изоляция (D)

- **D1. Папка данных** (`Storage:DataDirectory`, по умолчанию `%LOCALAPPDATA%\CoveyPlanner`):
  `accounts.db` — пользователи, коды, приглашения, сессии; `users\{UserId}.db` — данные пользователя (та же схема, что сейчас у `planner.db`);
  `backups\` — снимки; `mail\` — почтовый ящик разработки; `keys\` — ключи Data Protection (без них после перезапуска все cookie недействительны);
  `settings.json` — настройки этой установки вне git (почта администратора, SMTP); `local.key` — ключ служебных скриптов (D6).
- **D2.** `UserId` — GUID (по имени файла нельзя угадать соседа или число пользователей).
- **D3.** Контекст данных (`PlannerDbContext`) открывается на файл пользователя из сессии запроса. Нет пользователя — исключение, данные не открываются.
  Сервисы Core и репозитории не меняются.
- **D4. Миграции.** При запуске: `accounts.db`, затем каждый файл `users\*.db`; если у файла есть новые миграции — сначала снимок (как сейчас «перед-обновлением»).
  Ошибка миграции одного файла — сервер не стартует (лучше не запуститься, чем показать пустой планировщик).
- **D5. Бэкап — снимок папкой**: `backups\2026-10-22_221500-вручную\` с `accounts.db` и `users\*.db` (каждый через `VACUUM INTO`).
  Хранятся последние 30 снимков (`Storage:BackupsToKeep`), ежедневный — при запуске, как сейчас.
- **D6. Служебные скрипты.** `POST /api/backup` и `GET /api/backup` — администратор **или** заголовок `X-Planner-Local-Key` со значением из `local.key`
  (файл создаёт сервер; прочитать его может только тот, у кого есть доступ к диску сервера). `tools/backup.ps1` и `install.ps1` читают ключ из файла.
- **D7. Пересмотр.** При переходе на PostgreSQL или сотнях пользователей — отдельная спека: переход к «одна база + UserId».

## 5. Вход по коду (L)

- **L1. Экран входа** (вместо планировщика, если не вошли): «Почта» → «Получить код». Ответ всегда один и тот же:
  «Если этот адрес зарегистрирован, код придёт в течение минуты» — по ответу нельзя узнать, есть ли такой пользователь. (предложение — вопрос 4)
- **L2.** Код — 6 цифр (`RandomNumberGenerator`), письмо «Код входа: 123 456». Действует **10 минут**, одноразовый; новый код отменяет прежний.
- **L3.** В базе — только `HMAC-SHA256(ключ сервера, почта + код)`; ключ — в `keys\`, не в `accounts.db` (утечка одной базы не даёт подобрать код).
- **L4.** Ввод кода: «Код из письма» (6 полей-клеток, вставка целиком, цифры с пробелом тоже). Неверно — «Неверный код, осталось попыток: 3».
  **5 неверных попыток** — код сгорает: «Код больше не действует — запросите новый». Истёк — то же.
- **L5. Частота.** По почте: не чаще 1 кода в 60 с и 5 в час («Новый код можно запросить через 42 с» — кнопка с отсчётом).
  По адресу: 20 запросов кода в час, 50 проверок кода в час. Превышение — 429, «Слишком много попыток, попробуйте через N мин».
- **L6.** Почта сравнивается в нижнем регистре, без пробелов по краям. Отключённому пользователю код не отправляется (ответ — как в L1).
- **L7.** Успешный вход: сессия (S), `LastLoginAt`, возврат туда, откуда пришли (или к неделе).

## 6. Сессии (S)

- **S1. Cookie** `planner.session`: HttpOnly, `SameSite=Lax`, `Secure` — при HTTPS (`SameAsRequest`; в проде — всегда), путь `/`.
  Внутри (зашифровано Data Protection) — UserId и SessionId; на сервере — строка `Sessions`.
- **S2. Срок: 90 дней, скользящий** — каждый день работы продлевает; не заходили 90 дней — вход заново. Абсолютный предел — **1 год**
  (раз в год вход кодом обязательно). (предложение — вопрос 2)
- **S3.** Каждый запрос проверяет, что сессия не отозвана и пользователь не отключён (одна строка из `accounts.db`); `LastSeenAt` обновляется не чаще раза в 5 мин.
- **S4. «Выйти»** — эта сессия. **«Выйти на всех устройствах»** — все сессии пользователя, включая эту; вопрос «Выйти на всех устройствах? Понадобится снова войти кодом».
- **S5.** У сессии хранится подпись устройства из User-Agent («Edge · Windows», «Safari · iPhone»), даты входа и последней активности. IP не храним.

## 7. Приглашения (I) и режим регистрации

- **I1.** Режим — `Accounts:Registration` = `Invite` (по умолчанию) | `Open`. Меняется настройкой и перезапуском. Экранов для `Open` нет, кроме того, что L1 создаёт аккаунт.
- **I2. Создать** (админка): «Почта (необязательно)», «Срок: 7 дней ▾» (1, 3, 7, 14, 30). Ссылка `…/invite#<токен>` показывается **один раз**
  с «Копировать»; в базе — только хэш токена. Привязано к почте — письмо с ссылкой уходит само. (предложение — вопрос 5)
- **I3. Список**: «Активные» · «Использованные» (кем и когда) · «Истёкшие» · «Отозванные»; у активного — «Отозвать».
- **I4. По ссылке**: «Вас пригласили в планировщик» → почта (если приглашение с почтой — подставлена и не меняется) → код (L2–L5) → аккаунт со стартовым набором (N), вход.
  Приглашение тратится **только при успешном коде**. Почта уже зарегистрирована — «У этого адреса уже есть аккаунт · Войти», приглашение не тратится.
- **I5.** Истекло / использовано / отозвано / нет такого — одно сообщение «Приглашение не действует — попросите новое».
- **I6. Open**: L1 с незнакомой почтой отправляет код; после кода — аккаунт со стартовым набором. Приглашения в `Open` работают как раньше.
- **I7. Первый администратор** — `Accounts:AdminEmail` в `settings.json` (D1): если пользователей нет, сервер создаёт администратора с этой почтой
  (и переносит данные — X). `install.ps1 -AdminEmail …` записывает её туда один раз. Нет пользователей и нет настройки — экран входа: «Администратор не задан: см. README».

## 8. Пользователи (U)

- **U1. Админка** — пункт «Пользователи и приглашения» в «⚙ Настройки» (только у администратора), экран поверх недели, вкладки «Пользователи» · «Приглашения».
- **U2. Список**: почта, дата регистрации, последний вход, «администратор», «отключён»; «Отключить» / «Включить».
- **U3. Отключить** — все сессии сразу отозваны, вход невозможен; данные не трогаются. Себя отключить нельзя (кнопки нет).
- **U4.** Чужих данных администратор не видит: админка показывает только аккаунты, не планировщик.

## 9. Стартовый набор (N)

- **N1.** Новый пользователь получает: 4 измерения пилы (Тело, Ум, Дух, Общение и эмоции — цвета как сейчас), роли **«Я», «Семья», «Работа», «Дом»**
  и категории ленты **«💡 Идеи»**, **«📚 Почитать»**. Целей, дел и привычек нет. Настройки — по умолчанию. (предложение — вопрос 3)
- **N2.** Стартовый набор создаётся вместе с файлом пользователя, один раз; `SeedData` при запуске сервера больше не нужен.

## 10. Письма (M)

- **M1.** `IEmailSender` — интерфейс; реализации: `Folder` (почтовый ящик разработки) и `Smtp`. Выбор — `Mail:Mode` (по умолчанию `Folder`).
- **M2. Почтовый ящик разработки**: письмо — файл `mail\2026-10-22_221500_a***.eml` (открывается почтовой программой) и строка в `mail\index.txt`.
  Страница `/dev/mailbox` (последние 20 писем, свежие сверху) — только в режиме `Folder` и только для запросов с этого компьютера без заголовков прокси;
  на экране входа в режиме `Folder` — ссылка «Письмо — в почтовом ящике разработки».
- **M3. SMTP** — `Mail:Smtp:Host`, `Port`, `User`, `Password`, `From`, `UseTls` — в `settings.json` или переменных окружения, не в git.
  Провайдер — при деплое. В режиме `Smtp` письма в папку не пишутся.
- **M4.** Письма — короткие, на русском, без отслеживания: «Код входа: 123 456. Действует 10 минут. Если вы не входили — просто удалите письмо.»

## 11. Аккаунт и «какие данные храним» (P)

- **P1. «Аккаунт»** — пункт в «⚙ Настройки» (и строка почты в шапке настроек): почта; «Устройства» — список сессий (S5), «это устройство», «выйти» у каждой;
  «Выйти» · «Выйти на всех устройствах».
- **P2. «Выгрузить мои данные»** — файл `coveyplanner-2026-10-22.json`: `{ format, version: 1, exportedAt, account: { email, createdAt }, settings,
  roles, categories, tasks (с корзиной, ролями, целью, шагами), goals, series, vacations }`. Только чтение; загрузки обратно сейчас нет.
- **P3. «Удалить аккаунт»** — окно: что удалится; «Чтобы подтвердить, введите свою почту»; кнопка «Удалить навсегда» (розовая) активна только при совпадении.
  Удаляются: файл данных, сессии, коды, строка пользователя. Без «Вернуть». Единственный администратор удалить себя не может («Сначала назначьте другого администратора» — назначение не делаем, значит, кнопка неактивна). (предложение — вопрос 6)
- **P4. «Какие данные мы храним»** — страница `/privacy` (открыта без входа, ссылка с экрана входа и из «Аккаунта»): почта; дела, цели, роли, категории, настройки;
  устройства входа (браузер и система, даты); не храним: пароли, IP-адреса, аналитику, рекламу; письма — только код и приглашение;
  как выгрузить и удалить; резервные копии хранятся до 30 последних снимков (около месяца), потом удаляются сами.

## 12. Очередь изменений и истёкшая сессия (Q)

- **Q1.** Ответ 401 на изменение — как «нет связи» (BN): изменение остаётся в очереди, следующие встают за ним; поверх экрана — окно входа
  (почта подставлена) **без перезагрузки страницы** — очередь живёт в памяти и при перезагрузке пропала бы.
- **Q2.** Плашка вверху (`--warn`): «Вы вышли — изменения не сохранены (3). Войдите, чтобы сохранить». Закрыть вкладку — браузер спрашивает (как сейчас).
- **Q3.** Вошли **тем же** пользователем — очередь уходит по порядку, «Сохранено 3», экран перечитан.
  **Другим** — очередь не отправляется: «Изменения прежнего аккаунта (3) не сохранены — они были для другого пользователя», экран перечитан.
- **Q4.** 401 на чтение — то же окно входа; после входа — перечитать.
- **Q5.** Отключённый пользователь — окно входа с «Аккаунт отключён — обратитесь к администратору»; очередь не отправляется.

## 13. Перенос данных Анны (X)

- **X1.** Первый запуск новой версии, пользователей нет, `Accounts:AdminEmail` задан, есть `planner.db`: создаётся администратор,
  `planner.db` копируется (`VACUUM INTO`) в `users\{UserId}.db`. Сам `planner.db` не удаляется и не меняется — переименовывается в
  `planner-before-accounts.db` (откат — вернуть имя и поставить прежнюю версию).
- **X2. Сверка** — до и после: число строк каждой таблицы (13) и контрольная сумма содержимого каждой (строки по ключу → SHA-256);
  должны совпасть все. Не совпало — перенос отменяется, сервер не стартует, причина — в журнале.
- **X3.** Сначала — на **копии** базы: `Planner.Server.exe --migrate-accounts --data-dir <копия> --admin-email <почта> --report <файл.md>`;
  отчёт Анне (числа до/после). Только потом `install.ps1` на настоящих данных.
- **X4.** В браузере после установки — вход кодом (почтовый ящик разработки), всё на месте.

## 14. Обязательные тесты (T)

- **T1. Все маршруты закрыты.** Тест перечисляет `EndpointDataSource`: каждый `/api` маршрут либо требует вход, либо в явном списке открытых
  (L, I, ping, privacy); админские — политика `Admin`. Новый маршрут без пометки — тест падает.
- **T2. А не видит и не меняет данные Б.** Пользователь А создаёт полный набор (дело, мысль, шаг, проект, категория, роль, цель, серия-привычка,
  каникулы, миссия) с меткой «СЕКРЕТ-А». Для **каждого** маршрута из `EndpointDataSource` — пример запроса с Id из набора А (таблица примеров;
  маршрута нет в таблице — тест падает). Б выполняет все. Проверка: ни в одном ответе нет «СЕКРЕТ-А»; выгрузка А (P2) до и после — побайтно одинакова.
  Админские маршруты от не-администратора — 403.
- **T3. Вход и приглашения**: код 10 мин (сдвиг часов), 5 попыток, новый код отменяет старый, в базе нет кода открытым текстом, частота по почте и по адресу (429),
  отключённый, CSRF (нет заголовка — 400), 401 без входа, «выйти», «выйти везде», скольжение и предел срока; приглашения — с почтой (чужая почта — нельзя),
  без почты, истекло, использовано, отозвано, уже зарегистрирован, `Open`.
- **T4. e2e**: `login` — настоящий вход через почтовый ящик разработки; `invite` — администратор создаёт приглашение, второй браузер регистрируется;
  `session-expired` — сессию отозвали посреди работы → окно входа → изменения досланы (Q3), вход другим — не досланы; `account` — устройства, выгрузка, удаление.
  Остальные сценарии входят через `/api/dev/login`.
- **T5. Перенос** (X): тест мигратора на базе из `MigrationTests` — числа и суммы совпадают; повторный запуск ничего не делает.

## 15. Крайние случаи

- Два устройства, одно «выйти везде» — второе на следующем запросе получает 401 → Q.
- Код запросили, потом пришло приглашение на ту же почту — код действует для входа только если аккаунт уже есть; регистрация — только через ссылку (`Invite`).
- Пользователь удалил аккаунт, у него открыта вторая вкладка — 401, окно входа; войти нельзя (L1-ответ).
- Перенос прерван посередине — `planner.db` не тронут, `users\` и `accounts.db` удаляются, следующий запуск начинает заново.
- Общий браузер, два пользователя по очереди: настройки вида в localStorage (тема, свёрнутые роли, вкладка) — общие для браузера, не данные; Id ролей у разных
  пользователей могут совпасть — в худшем случае у второго свернётся «чужая» по номеру роль. (предложение — вопрос 9)
- Часы сервера сдвинуты (`/api/dev/clock`, только Development) — сдвигаются и сроки кодов (тесты T3 этим и пользуются).

## 16. Что НЕ делаем

Деплой, домен, HTTPS-сертификаты, название; открытую регистрацию как экран (только переключатель); пароли, соцсети, passkeys; оплату;
смену почты; назначение других администраторов; загрузку выгрузки обратно; аудит-журнал действий; общий доступ к данным между пользователями.

## 17. Критерии готовности

- Без входа не открывается ни один маршрут данных (T1); А не видит и не меняет Б (T2); тесты T3, T5 и e2e T4 зелёные; весь прежний e2e зелёный.
- Данные Анны перенесены, сверка на копии и на настоящих данных совпала, отчёт у Анны.
- README: папка данных, вход, почтовый ящик разработки, `settings.json`, SMTP, бэкап и восстановление снимка. CLAUDE.md — §1, §2, §5 (модель), новый раздел про аккаунты.
